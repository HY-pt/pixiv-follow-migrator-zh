### 6. 导入回去顺序会颠倒（v3.1.1 修复）

**先回答：导入导出本身没有排序问题** —— 两个版本的通篇代码里没有一处 `sort` / `reverse`，
导出是原样 `JSON.stringify(list)`，导入是 `for...of` 顺序遍历后 `push`，数组顺序严格保持。

**倒序来自 pixiv 的显示规则**：关注列表是「**最新关注的排最前**」。
抓取时按接口返回顺序（最新 → 最早）入库，如果就照这个顺序依次关注，
每关注一个人就插到目标账号列表最前，整批做完后**显示顺序恰好完全翻转**。

实测（5 人）：

```
源账号显示（接口顺序）: 最新E → D → C → B → 最早A
正序关注后目标账号    : 最早A → B → C → D → 最新E   ← 完全颠倒
反序关注后目标账号    : 最新E → D → C → B → 最早A   ← 与源一致 ✓
```

新增「**关注顺序**」下拉，默认「还原原账号顺序（推荐）」，即从**最早关注的**开始关注，
最后关注的那位才会排在最前。想让顺序颠倒（或你本来就按新→旧整理过）就选「按列表顺序」。

注意这有个前提：源账号的接口顺序本身就是「新→旧」。如果你之前用旧版跑过一次、
列表已经是颠倒的，那反过来选一下即可。

### 7. 公开/私密是分开关注的（回答提问）

**是的，分别按各自的可见性关注，不靠全局下拉框。**
抓取时 `restrict=show` 与 `restrict=hide` 分两次拉取，存进列表时每条带自己的 `restrict` 字段；
关注时 `fd.append('restrict', u.restrict)` 用的是**这一条自己的值**。
右下角「默认可见性」只对**没有标记**的记录（比如手工导入的裸数据）生效。

所以公开关注和私密关注各自独立成组，互不影响；导出时也能分开出两个文件。

## v3.5.0：导入语义纠正为「增量覆盖」

上一版我把三个选项做成「自动 / 全公开 / 全私密」，语义偏了。你要的是原版作者那套能力的整合：

| 选项 | 含义 |
| --- | --- |
| **全部** | 总表：按文件里每条自己的公开/私密标记；没标记的算公开 |
| **公开** | 把这份文件**并入「公开关注表」** |
| **私密** | 把这份文件**并入「私密关注表」** |

### 「增量覆盖」具体是这三条

这是本次真正的行为改动（之前是「已存在就跳过」）：

| 情况 | 旧行为 | 新行为 |
| --- | --- | --- |
| 文件有、列表没有 | 追加 | 追加 ✓ |
| 文件有、列表也有 | **跳过（可见性不更新）** | **覆盖可见性**（以文件为准） |
| 列表有、文件没有 | 保留 | 保留（**绝不清空**） |

举例：列表里 `2` 本来是私密，导入一份「公开」表且里面包含 `2` → `2` 会变成公开。
而列表里不在文件中的其他人**原样保留**——这才叫「增量覆盖」，不是「替换整表」。

状态栏会报明细：

```
📂 导入完成（并入「公开」）：新增 1，改可见性 1；列表共 4 位（公开 3 / 私密 1）
```

### 与作者原版的关系

原版的做法是：`Visibility` 下拉 + 「开始自动关注」，**手动切两次、跑两趟**，分别按公开/私密关注。
现在把这套能力整合成：**导入时选一次表类型，之后按每条自己的标记去关注**。

所以现在不需要手动跑两趟了——导入时标明这份文件属于哪张表，列表里就带上了正确的 `restrict`。

**② `<details>` 折叠根本没生效**

## v3.4.0：校验与销毁分离、长休眠、三种撞墙策略、导入三选一

### 1. 「列表自毁」的真凶：校验直接写盘 + 关注前偷偷删人（两处）

原来的 `verifyAgainstAccount` 一句话就删：

```js
const remain = before.filter(u => !have.has(u.id));
if (removed > 0) saveList(remain);   // ← 无中间态、无备份、不可撤销
```

更隐蔽的是**第二处**：每次点「开始自动关注」前会自动跑一次同样的逻辑，
用户完全没察觉列表就被削减了。你导入的 72 公开 + 21 私密「自毁」，这两处都可能是原因。

**现在拆成三个独立按钮**：

| 按钮 | 行为 |
| --- | --- |
| 🔍 校验并生成报告（不改列表） | 只比对、只出报告（N 位已关注 / M 位待关注），列表一个字不动 |
| 🗑 执行清理（移除已关注） | 按上次报告真正删除，**删除前自动备份**，有二次确认 |
| ↩️ 撤销清理 | 一键恢复到清理前 |

另外加了**三重保险**：
- 目标账号读回 **0 条**时直接中止校验（`可能未登录或被限流，已中止比对以免误删`）；
- 关注前的自动比对改成**只跳过、不删除**；
- 报告存到 `pfm_verify_report`，清理必须基于一份**有效报告**才执行。

### 2. 长休眠：每 N 个休息 M 秒

新增两个输入：**每 N 个长休眠**（默认 50）、**长休眠时长（秒）**（默认 30）。
到点会显示 `😴 已完成 50 个，长休眠 30 秒…`，期间可随时点「停止」。
填 0 即关闭。这是 [PixivBatchDownloader 的「慢速模式」](https://github.com/xuejianxianzun/PixivBatchDownloader) 思路。

### 3. 默认间隔 650ms → 1200ms

调研发现 PBD 用**固定 1600ms 仍有人报 429**，说明节奏规律性也在被检测。
650ms 明显偏激进。基准改 1200ms，配合 1～3 倍随机抖动，实际落在 1200～3600ms。

### 4. 三种撞墙策略（你说的「两种方案都做」）

| 策略 | 行为 | 代价 |
| --- | --- | --- |
| **暂停等待后自动续跑**（默认） | 冷却 3~5 分钟后原地重试 | 无，最安全 |
| 立即停止，保留进度 | 直接停，等你手动再点 | 无，但要人工介入 |
| 取消关注再关注回来 | `remove_bookmark_user` → 等 3~5 秒 → 重新 `add_bookmark_user` | **对方会收到重复关注通知** |

关于第三种方案，查到明确证据：pixiv **取消关注不发通知，但重新关注会发**。有用户因为被反复取消/关注而投诉甚至拉黑：

> 「フォローしては外してを繰り返す人が居て、それが毎度通知に来るので鬱陶しくて一度だけブロックした」
> —— [Yahoo!知恵袋](https://detail.chiebukuro.yahoo.co.jp/qa/question_detail/q14316179304)

所以它**不是默认值**，选中时确认框里会明确写「对方会收到重复关注通知，请谨慎」。

### 5. 导入可见性三选一

原来的「默认可见性」下拉确实有误导性 —— 它只对没有标记的记录生效，导两张分表时还得逐条改。

现在导入时按文件内容自动判断并询问：

- 文件里**带 `restrict` 字段** → `确定 = 按标记导入（推荐）` / `取消 = 全部当作私密`

对应你说的「总表 / 公开分表 / 私密分表」三种情况。

## v3.3.2：私密关注被抓成 0/23（我上一版引入的回归）

### 根因：`TAIL_EMPTY` 判定漏了「第一页就空」这一种

v3.3.1 我为了处理「注销账号占着 total」的情况，加了这条判断：

```js
if (total !== null && offset < total) reason = 'TAIL_EMPTY';   // ← 漏了 offset === 0
```

`offset = 0` 时 `0 < 23` 同样成立，于是**私密关注第一页返回空就被判成「已到尾部、正常损耗」**，
状态栏显示 `私密 0/23（0 页）` 还报「抓取完成」，游标也被清掉。

**实际上第一页空绝不可能是「尾巴」** —— 那是请求本身失败（未登录、接口异常、权限不足）。

**修法**：把两种情况分开判断：

```js
if (!users.length) {
  if (offset === 0) reason = lastErr || '第一页就返回空（可能未登录、接口异常或权限不足）';
  else if (total !== null && offset < total) reason = 'TAIL_EMPTY';   // 只有超过 0 才算正常损耗
  break;
}
```

另外把私密抓取的 `catch (_) {}` 改成**显式记录错误**——原来静默吞掉异常，
界面上只表现为「私密 0/23」，完全看不出是失败了。

### 你现在该怎么操作

**旧版留下的坏游标要清掉**：v3.3.1 可能已经把 `pfm_cursor` 写成 `{show:0, hide:0}` 甚至清空。
装上 v3.3.2 后，如果私密仍显示 `0/23`，点一次「查看列表 → 全部清空」旁边的思路不管用 ——
直接重新点「自动抓取全部」即可，它会从 offset 0 重新拉私密。

实测（假后端：公开 30 位正常、私密 total=23 但永远返回空）：

| 断言 | 结果 |
| --- | --- |
| 不报「抓取完成」 | ✓ 报「⚠️ 未抓全」 |
| 说明原因 | ✓「第一页就返回空（可能未登录、接口异常或权限不足）」 |
| 游标保留未完成状态 | ✓ 未清除 |

## v3.3.1：差额归因（注销/冻结账号）+ 修掉一个错误的提示文案

（「数字对不上通常是对方账号被冻结」）。

另有 公开缺 1、私密缺 2 位取不到 —— 这是已注销/被冻结的账号，

## v3.3.0：深翻页提前中断 + 断点续抓

### 「95/128（4 页）」的成因：不足 24 条就 break

上一版有个致命假设：把「本页不足 `limit` 条」当成「已经到底」。

```js
if (users.length < PFM_PAGE) break;   // ← 错！深翻页时服务端会返回不满的页
```

pixiv 深翻页时会返回**不满 24 条**的分页（比如第 5 页只给 12 条）。旧逻辑据此判定结束，
于是稳定停在 4 页 × 24 ≈ 96 条 —— 你截图里的 `公开 95/128（4 页）` 正是这个。

**修法**：不再用「不满页」判断结束，改成：

- 翻页进度按**实际返回条数**前进（`offset += users.length`，不是 `+= limit`），不满页也不会漏尾部；
- 只有**空页**、**整页重复**（连续 2 次）或 **offset 达到 total** 才结束；
- 空页但 `offset < total` 时，明确报「在 offset=N 处返回空页（服务端对深翻页有限制）」，不假装成功。

实测复现（假后端 200 公开+50 私密，从 offset 96 起每页只给 12 条）：

| | 结果 |
| --- | --- |
| 旧逻辑（不满页即停） | 停在第 4 页 ≈96 条 —— 与你的截图一致 |
| 新逻辑 | 公开 200/200（**13 页**）· 私密 50/50（3 页）= 250 条 ✓ |

### 断点续抓：不再永远从第一页开始

**这就是你提到的「允许脚本发现当前页码，从当前页码继续往后抓」**。

现在每次抓取都会把 `{userId, show, hide}` 存进 `GM` 存储的 `pfm_cursor`：

- 抓取中断（限流/网络/翻页失败）时**保留游标**，状态栏直接告诉你下次从第几位接着抓；
- 再点「自动抓取全部」会**从游标处继续**，不会从 offset 0 重来；
- 全部抓完后自动清除游标，下次是全新一轮。

实测（第 4 次请求起强制 429）：

```
第一次：入库 72，游标 {"show":72}，提示「再点一次会从第 72 位继续」
第二次：首个请求就是 following?offset=72&limit=24 ← 从断点接上，最终 250/250 ✓
```

**所以遇到「只能翻 4 页」不用改脚本也不用手动抓**：多点几次，每次都会往前推进一段，
直到状态栏显示「抓取完成」。

### 「抓取当前页」的页码提示

面板现在会显示是第几次抓取的（URL 里有 `p=` 参数时显示「第 N 页」），配合顺序提示，
你能确认自己抓到哪一页了。

## v3.2.0：分页只取到 100 的真相 + 抓取当前页的顺序说明

### 「每张表只能抓 100 个」——是 `limit=100` 导致 offset 失效

之前我把这误判成「原版中途 error 就退出」。真正原因是：**这个接口在 `limit=100` 时，
服务端会忽略 `offset`，每次都只返回第一页**（100 条），于是翻页翻不动，永远停在 100。

证据：[PixivFE 的 commit `6758f2e`](https://git.gay/kita/PixivFE/commit/6758f2e3a31c197661f2bf2eb8402e5af844e292.patch)
把关注接口的 `limit=100` 改成了 `limit=12`，同一次提交里的注释写作 `API uses limit=12` ——
100 是个坏边界值。

**修法**：改用 `limit=24`（pixiv 前端自己在用的量级），offset 才可靠。
另加**翻页失效检测**：第二页起若返回内容与上一页完全相同，立刻中断并明确报错
`翻页未生效（服务端返回了重复的一页，offset 被忽略）`，绝不把重复数据堆成假结果。

实测（假后端 200 公开 + 50 私密）：

| 场景 | 结果 |
| --- | --- |
| 正常 | 公开 200/200（9 页）· 私密 50/50（3 页），共 250 条 ✓ |
| 强制 offset 失效 | 抓 1 页即中断，入库 48，明示原因 ✓（旧逻辑会静默卡在 100 还报成功） |

**所以不需要手动抓了**，超过 100 个也能一次跑完。状态栏会报
`公开 200/200（9 页）· 私密 50/50（3 页）` 这类可核对明细。

### 「抓取当前页」的顺序从哪来

**它不知道全局顺序，靠的是「追加」这个动作本身。**

pixiv 关注页是 `1 → N` 由新到旧。DOM 里读不到「这是第几位」这种全局坐标，
也读不到公开/私密标记。所以：

- **顺序**：只要从**第 1 页开始按顺序**逐页点「抓取当前页」，每页内部按 DOM 顺序 push，
  拼起来就是完整的「新→旧」顺序，与 API 结果一致。跳页或乱序点会破坏这个顺序。
- **可见性**：DOM 区分不出公开/私密，这一页抓到的全部按**「默认可见性」**打标，
  事后可在列表弹窗里逐条点标签改，或直接用「自动抓取全部」拿准确标记。

面板已明确提示这个局限，不再让人误以为拿到了完整信息。

实测（模拟 DOM 7 个链接）：

```
DOM 顺序: 最新E → D → C → B(alt) → 最早A → 最新E重复 → 我自己
抓到:     最新E → D → C → B(alt) → 最早A     ← 顺序一致、去重、排除自己 ✓
可见性:   全部按默认值打标 ✓
```

**建议**：「自动抓取全部」准确、完整、带可见性，优先用它；「抓取当前页」只用于
想取特定页面区间、或 API 抽风时兜底。

## v3.1.0 改了什么

### 1. 抓取只翻一页就停（原版 bug）

原版这段的退出条件：

```js
if (json.error || !json.body?.users) break;   // 任何一页出错就静默退出
...
if (users.length < limit) break;
```

pixiv 的关注接口单页上限 100，必须靠 `offset` 翻页。原版只要某一页返回 error 就直接 `break`，
而且**界面上照样报「抓取成功」** —— 这就是「只能拉到 100 位」的来源。

现在：翻页直到取满 `total`，每页失败重试 3 次，429/403 按退避等待；
真拿不全时状态栏会说明中断原因和已拿到的数量，不再假装成功。

### 2. 关注节奏太规律，55 个就被限流

原版是 `650ms + Math.random()*150` —— 均匀抖动，机器特征很明显。

现在新增 **「抖动上限（倍）」** 输入框（默认 3）：实际间隔在 `650ms × [1, 3]` 之间随机，
连续失败还会指数退避（最多 60 秒）。撞到 429/403 立即停止并提示等 10～30 分钟，
不再继续硬撞把账号限制坐实。

### 3. 撞墙后列表不会全丢

现在只有**确认成功**或**确认已关注**的记录才从列表移除；失败、被限流中断、还没轮到的**一律保留**，
状态栏会写明「未完成 N 位仍在列表里（公开 X / 私密 Y）」。

另外新增 **「✅ 校验并清理已完成」** 按钮，也是每次「开始自动关注」前的自动步骤：
先拉一次目标账号现有的关注列表，把已经在里面的人从待办里剔除。
所以中断后重跑不会重复撞同一批人，列表会自然收敛。

### 4. 公开 / 私密自动分开

原版抓取时把 `restrict=show` 和 `restrict=hide` 混成一个列表，之后只能手动切下拉框跑两遍。

现在每条记录自带 `restrict` 字段：抓取时公开关注标 `0`、私密关注标 `1`，**分别入库**。
自动关注时**按每条自己的可见性发送**，全局的「默认可见性」只对没有标记的记录生效。
列表弹窗里每条带公开/私密标签（点一下就能改），支持「全部 / 公开 / 私密」筛选，
导出时可选**分开导出两个文件**或合并成一个。

### 5. 执行锁

抓取、关注、校验三个动作共用一把锁：正在跑的时候再点任何一个，只会提示
「⏳ 正在执行「自动关注」，请等它结束」，不会重复发起请求。

### 6. 顺带修的界面问题

- **窗口不最大化时无法最小化**：面板原来没有高度上限，视口一矮，标题栏连 `—`/`✕` 一起被顶出屏幕外，
  被 `overflow: hidden` 裁掉。现在面板限高 `calc(100vh - 40px)`、标题栏常驻、内容区内部滚动。
- 拖动时把面板夹在视口内，窗口缩放时自动拉回可见区域。
- 字体栈加 `Microsoft YaHei / 微软雅黑 / PingFang SC`。

## 没改什么

`@match`、`@grant`、`@run-at`、CSRF 令牌拦截、pixiv 的接口地址与请求体格式、存储键 `pfm_list`
—— 一律沿用原版。抓取的对象是**当前登录账号**的关注列表（迁移就是从自己账号搬到另一个账号，
这里就该用登录身份，原版的取值顺序是对的，我特意没动）。
