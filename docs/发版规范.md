# 发版规范

本文件规定**版本号怎么走**和 **Release 说明怎么写**。改脚本、发新版前先读这里。

体例参考：

- [发布说明标准（Release Notes Style Guide）](https://github.com/imhaoyan/deepseek-harness-launcher/blob/main/docs/release-notes-style.md)：标题纯版本号、分组写用户能感知的变化、条目上限
- [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)：新增 / 变更 / 修复 / 移除 的分组语义
- [GitHub Release Notes Conventions](https://github.com/flc1125/skills/blob/main/skills/github-release-notes-writer/references/release-notes-conventions.md)：用最少的小节把版本讲完，空小节不写

---

## 一、版本策略

**发布只发功能版（`X.Y.0`），或维护者指定的版本号。本地修复可以自由升补丁号。**

| 情况 | 版本号 | 是否发 Release |
| --- | --- | --- |
| 新增功能、界面改版、行为变更 | 升 `Y`，例如 3.7.0 → 3.8.0 | 发 |
| 同一功能线内的修补、文案、图标、像素级调整 | 可升 `Z`，例如 3.7.0 → 3.7.1 | **不发**，随下一次功能版一起发 |
| 线上事故、安全、数据错误 | `X.Y.Z` | 另行商定 |

要点：

- **本地构建可以随时升补丁号**，用于区分构建与本地验证，不必顾虑会污染发布历史。
- **发布只在功能版本或明确指定版本号时进行**；不要因为一个小修就单独开 Release。
- **已发布的 Release 内容不再改动**：不要用 `--clobber` 把后续本地修复塞进旧版本；这些修复随下一次功能版发出。
- 发布时若本地已累积补丁号（如 3.7.3），功能版号仍取下一个 `X.Y.0`（3.8.0），自然大于它们，更新链不会断。
- 真正发布的那一版，`@version` 必须与 tag 一致；改了版本号要回写生成器再重建，不手改产物。
- Release 附件固定两个：`pixiv-follow-migrator-zh.user.js` 与 `pixiv-follow-migrator-zh.meta.js`。
- Greasy Fork 是面向用户的更新源（站内托管 `@updateURL`），GitHub Release 提供文件快照。
- 已发布的 Release 不删；确需下线时在此文件「事故记录」说明。

## 二、Release 说明格式

**标题只写版本号**，不加副标题：

```
v3.7.0
```

**正文从分组开始，不重复版本号**——GitHub 页面标题已经显示了版本号，正文再写一遍就会出现两个标题。正文首行只留一行日期备注（`> 发布于 YYYY-MM-DD`）。

```markdown
**新增**
- 每行一条，动词开头，句末不加句号

**优化**
- …

**修复**
- …
```

分组只用这四个，**空分组不写**：

| 分组 | 放什么 |
| --- | --- |
| 新增 | 用户能用的新能力 |
| 优化 | 既有功能变得更好用（文案、布局、提示） |
| 修复 | 用户能感知的错误行为被纠正 |
| 移除 | 删掉的功能或控件 |

### 写作规则

写**用户能感知的变化**，不写实现细节。

| 要写 | 不要写 |
| --- | --- |
| 逐页抓取改按当前标签页自动判断公开/私密 | 读 `location.search` 里的 `rest=hide` 判断 |
| 关注时「公开」用户被误按「私密」关注的问题 | 删掉 `defaultRestrict` 读取逻辑 |
| 重复抓取同一页时误报「新增 0 位」 | 状态栏字符串模板调整 |

- 不出现文件名、函数名、行号、提交号、测试结果、根因分析。
- 术语用界面上的原词（「校验关注状态」「移除已关注记录」「高级」），不要用代码里的叫法。
- **一个用户能理解的功能点 = 一条**；同一功能的不同细节合并成一条，不按提交或界面角落拆条。
- 每条一行、尽量 ≤ 40 字；一个版本通常 3–8 条，**上限 10 条**。

### 存档

每个已发布版本的说明原文存 `docs/release-notes/vX.Y.Z.md`，发版时直接用它当 `--notes-file`，不再另写一份。

## 三、发布流程

1. 改 `src/生成脚本-patch.js` 里的 `@version` 与标题栏版本标签
2. 写 `docs/release-notes/vX.Y.Z.md`，并在 `CHANGELOG.md` 追加同版本条目
3. `node src/生成脚本-patch.js` → 必须输出「全部替换成功，无未匹配项。」
4. `node --check pixiv-follow-migrator-zh.user.js`，再跑 `tests/` 全部脚本
5. **脱敏扫描**（本地用户名 / 绝对路径 / token / 邮箱 / 内网地址 / 会话记录片段），报告不随仓库分发——先扫后传
6. 推送 main
7. 发版：

```bash
gh release create vX.Y.Z --title "vX.Y.Z" --target main \
  --notes-file docs/release-notes/vX.Y.Z.md \
  pixiv-follow-migrator-zh.user.js pixiv-follow-migrator-zh.meta.js
```

8. 核对 `gh api .../releases/tags/vX.Y.Z` 里附件的 `size` 与 `digest`，与本地 `sha256sum` 一致
9. 回读远端 raw 文件的 sha256，与本地产物比对
10. **同步 Greasy Fork**：在脚本页点「更新脚本」上传同一份 `pixiv-follow-migrator-zh.user.js`（站内 ID 不变）；GF 会自动注入 `@updateURL` / `@downloadURL`，仓库文件不含这两个字段
